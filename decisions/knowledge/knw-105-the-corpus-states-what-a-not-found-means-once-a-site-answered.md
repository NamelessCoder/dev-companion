# D-KNW-105 — The corpus states what a not-found means once a site answered

**The corpus explains a not-found by naming the site that should have answered,
and says nothing about the page that would not come.**

So a session holding a request the right site answered is routed through four
site configurations, none of which is wrong. The fact that would settle it was
written down once, in a hint about writing a seeding script.

## Evidence

- `datahandler-seeding` was the only entry that said a hidden page tree answers
  not-found, and its `appliesTo` is `seed`, `create pages programmatically`,
  `CommandLineUserAuthentication`. No query a session writes while a site is
  failing reaches any of them.
- The symptom cluster answers for the site alone. `site-base-collision` decides
  which of two sites answered, `installation-boot` the base that matches none,
  `initial-content-references` a base an import rewrote, and
  `autogenerated-site-configuration` a site the core wrote — and the skill lists
  those four for a request that reached the wrong site or none.
- The skill promised the other half and routed it nowhere. **The installation
  that already answers** says the line the page carries "separates a request
  that matched a site and failed inside it from one that matched none", and only
  the second half had a lookup.
- The messages are one set and were read on `.checkouts/12.4`, `13.4`, `14.3`
  and `main`. `PageResolver` answers `No site configuration found.` for a
  `NullSite` and `The requested page does not exist` where the router resolved
  nothing; `The requested page does not exist!` is the page that was found and
  withheld; `ID was not an accessible page` is the group check;
  `Page is not available in the requested language.` is the translation. All
  five are identical on all four.
- Every one of them is a response rather than an exception.
  `ErrorController::pageNotFoundAction()` renders the core error page and
  appends `Reason: <the message>` where the site configures no `errorHandling`
  for the code, on all four, and returns `{"reason": "..."}` for an
  `Accept: application/json` request. So the log stays empty and the rendered
  page is the only evidence, which is what `installation-exception-output`
  already sends a caller to look for.
- Hidden and deleted reach different distances, read on the same four.
  `PageSlugCandidateProvider` queries `pages` under `DeletedRestriction` and
  `WorkspaceRestriction` alone, so a hidden page routes and is refused after;
  `RootlineUtility` adds `DeletedRestriction` alone, so a hidden page stays a
  rootline entry while a deleted one breaks the rootline of everything below it
  and `SiteFinder::getSiteByPageId()` then finds no site for any of them.

## Decided

- A hint of its own, curated on the page rather than on the 404.
  `site-base-collision` holds the root-404 phrases and `D-KNW-098` measured what
  a second hint claiming them costs, so the vocabulary here is the message with
  its exclamation mark, a hidden or deleted root page, and a tree that is hidden
  everywhere.
- In `knowledge/hints/project.json` beside the cluster, not in
  `datahandler.json`. The caller arrives holding a request that failed, not a
  question about `DataHandler`.
- `hidden root page` and `root page is deleted` move off `site-base-collision`.
  They are the page's vocabulary and the collision keeps the site's.
- The four neighbours name it back, and two of them are corrected while they do.
  `installation-boot` said "a page-not-found" where the line is
  `No site configuration found.`, and `installation-exception-output` said the
  case "leaves nothing to read anywhere" where the reason line on the page is
  what it left.
- `datahandler-seeding` says "every page of that tree, its root included". A
  script that creates the root page creates it hidden too, so "below the root"
  named the one page that is not the exception.
- The doktype is stated and the registry behind it is not. A spacer and a folder
  produce the same sentence a hidden page does, which is the trap; which
  doktypes the check reads is another subject.

## Assumed

- That a hidden root page renders every page below it. The rootline entry is
  granted where `extendToSubpages` is 0 and nothing else in the chain consults
  the parent's disabled field, which was read rather than requested from a
  running installation.
- That the caller arrives with the message rather than with the page. What was
  measured is that the message reaches this hint and the site words still reach
  the collision.
- That the statement holds unbound. The messages, the restrictions and the error
  page are the same on `12.4`, `13.4`, `14.3` and `main`, and where the class
  carrying them differs no caller reads the class.

## Wrong if

- A hidden root page turns out to withhold its subtree on some path nothing here
  read — a rootline consumer, a TypoScript root template lookup, a menu. The
  first **Assumed** would be wrong and the statement is the opposite of what a
  caller needs.
- A session pastes the message and still lands on `site-base-collision`. The
  curation would be on the wrong words, and the message is what a failing
  request actually carries.
- The hint displaces `site-base-collision` on a plain root-404 query. The
  boundary `D-KNW-098` drew would be undone by the entry that leans on it.
- A caller reads the exclamation mark off a page whose site configures a 404
  handler and concludes from a message that is not there. The reading would need
  a step before it rather than a discriminator.
- The next session with a failing request reports that what it needed was which
  record to look at rather than what the message means. The gap would be in the
  procedure and a statement of meaning would not have closed it.
