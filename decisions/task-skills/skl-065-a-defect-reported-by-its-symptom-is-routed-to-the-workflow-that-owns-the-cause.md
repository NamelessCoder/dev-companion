# D-SKL-065 — A defect reported by its symptom is routed to the workflow that owns the cause

**Diagnosing a broken installation earns a route rather than a skill of its own,
because the half of it that has an order already has one published.**

Three tasks of one benchmark asked for the file and the cause with nothing
changed yet, and no published description covers that shape. Measured against
the server, what fails is the brief that answers such a request rather than the
absence of a workflow behind it.

## Evidence

- **The shape, as it stands on record.** `D-SKL-033` reads a benchmark outside
  this repository on 2026-08-19: seventeen project tasks, twelve skills listed
  and none loaded. Three of the seventeen were a page answering with an error or
  rendering the wrong thing, where the request was the file and the cause with
  nothing changed yet. The count and the shape are what is on record here; the
  prompts are not.
- **The half that has an order has it published.**
  `typo3-development-installation`'s **The installation that already answers**
  reads what the installation wrote down first, treats an empty log as a finding
  rather than as a missing file, fetches the rendered page only where nothing
  was written, and routes from the line it carries to
  `page-not-found-within-a-site`, `installation-boot`, `site-base-collision`,
  `autogenerated-site-configuration`, `project-configuration-files` and
  `typo3_configuration_lookup`. `D-SKL-059` is where that was put there.
- **The knowledge under it is the expensive half and is written.**
  `installation-exception-output` states where an uncaught exception is written,
  that the name of the file is an HMAC and is found as `var/log/typo3_*.log`,
  which codes are displayed and never written at all, and that
  `SYS/displayErrors` with the mask behind it decides whether the page carries
  the message.
- **What is left of the other half is one call and the caller's own checkout.**
  Once the symptom is placed in a subsystem, every remaining step is reading
  files this server says three times it does not read: the git state, PHP source
  as code, and the content itself. So there is no second order to write.
- **The placement call answers, and answers on a miss too.** Run against this
  checkout on 2026-08-19, `typo3_hint_lookup` with "the frontend page answers
  with an error and I need to find which file causes it" matches nothing and
  returns the index closest first, with `installation-exception-output` at the
  top of it. `bin/cli hints:probe` reaches `content-elements` from a content
  element rendering wrong, `datahandler-relations` from a field that does not
  save, and `caching` from a page serving the old content.
- **What fails is the route, and it fails towards writing.** Three
  `typo3_task_guide` calls, same day, same checkout, over stdio. "A content
  element renders the wrong markup on the page, find the cause" is recognized as
  adding or changing a content element and hands over
  `typo3-content-element-development`. "The backend module shows a blank page
  since the upgrade, find out why and report the file and the cause, change
  nothing" hands over `typo3-backend-module-development`. "The frontend page
  answers with an error and I need to find which file causes it, without
  changing anything" is recognized as nothing at all, matches no hint, and comes
  back with the checklist for writing a patch — keep it focused, add the
  narrowest useful coverage, draft the commit message.
- **The right answer is reachable only by naming it.** The same 500 task with
  `changeType="operations"` stated by the caller hands over
  `typo3-development-installation` and carries `installation-exception-output`
  with it. That argument is the answer the diagnosis is looking for.
- **The listing has no room for a fourteenth description.** The thirteen
  published ones cost 3966 characters against the 3970
  `SkillTest::everyDescriptionIsWrittenToTheBudgetTheyShare` allows, measured on
  2026-08-19 with that test's own arithmetic.

## Decided

- **No skill for the shape.** The installation half is a published workflow, and
  the other half is one lookup followed by reading the caller's own files, which
  is not an order anybody can get wrong in a way a skill would fix.
- **What it earns instead is an intent that changes nothing**, in
  `knowledge/task-intents.json`, plus the no-write brief behind it — the fourth
  after `audit`, `triage` and `installation-operations`. `TaskGuide` forks its
  skeleton on exactly that property today, so a request that asks for a cause
  stops being answered with the steps a patch owes.
- **Queued rather than built here.** The needles are measured against the corpus
  and against the cases that must keep missing (`D-SKL-011`, `D-SKL-039`), which
  is a change of its own; this entry is the reading that says it is the repair.
- **The case is written before any of it.** `SKILL-15` carries the prompt at
  contract `open`. `D-SKL-035` charges a new domain a run without the skill;
  this entry declines the domain, so what the case measures is the route.
- **Rejected: widening a published description.** Only
  `typo3-development-installation` is close, and it would have to name a content
  element rendering wrong — a side its body does not own, which is the failure
  `SkillTest::aBackendPreviewTaskMatchesTheSkillThatOwnsTheElement` was written
  for. Four characters of listing are what is left for it anyway.

## Assumed

- That the three benchmark tasks are the shape the todo describes. The benchmark
  is outside this repository, so the count and the shape were read from
  `D-SKL-033` and from the todo rather than from the prompts.
- That a diagnosis divides into those two halves. It is a reading of what the
  tools and the corpus answer, not of a recorded session doing one.
- That the cause of such a defect is inside TYPO3. A page broken by the web
  server, the container or the deployment is the same request with none of these
  answers behind it, and nothing here has measured how often that is the case.

## Wrong if

- A session with the intent in place still hand-reads its way to the cause
  without reaching either half's owner. Then the route was not the obstacle, and
  what is missing is an order after all.
- `SKILL-15` is run and the answer names a file and a cause that neither the
  installation half nor a subsystem hint could reach. Then the shape is wider
  than this entry read it.
- A second reported shape arrives where the work after the placement call is
  long enough to have steps of its own — following a value through the project's
  own PHP, say, which `SKILL-09` already shows a review getting wrong. Then the
  leftover is a workflow and this entry called it a lookup.
- The no-write brief is built and a diagnosis request still comes back with the
  patch checklist, because it was recognized by its subject first. Then the fork
  is in the wrong place and the intent alone does not reach it.

## Covered by

- `HintsTest::aRequestForACauseIsAnsweredWithWhatFindingOneNeeds`

## Since then

**2026-08-21**, the intent was built as `diagnosis` and `TaskGuide` gained the
fourth arm. What settled the needles is that two words carry the shape and no
sentence has to be enumerated, which is what `D-SKL-039`'s second **Wrong if**
asks for: `cause` and `causing` reach all three calls measured above and
`SKILL-15`, and across the 46 scenario prompts and the 26 one-kind briefs
`KnowledgeTest` held that day, neither reaches anything else. `why` was measured
on the same corpus, reaches one of the three and nothing else, and is in because
it is the other word the question is asked with. `diagnose` and `diagnosis` are
in as the change type, which exists for the reason `triage` does — a caller who
classifies rather than describes reaches for the value documented as writing no
file, and `D-GUI-011` is where they picked `audit`. `what is wrong` was measured
and rejected: it reaches `REVIEW-03`, which is a review.

The entry names no skill, and the needles are why. The same two words reach a
content element rendering wrong and an installation answering wrong, so an
unconditional route would hand the first of those the workflow that boots
something; what the installation half owns is stated as a step instead. The
other cost is stated rather than guarded: a request naming a cause and a fix in
one sentence — "find out why the frontend throws and fix it" — is answered as a
diagnosis unless the caller states the change type. That is `D-GUI-009`'s fork,
and the same exposure `audit` has carried since `R-GUI-006`.
