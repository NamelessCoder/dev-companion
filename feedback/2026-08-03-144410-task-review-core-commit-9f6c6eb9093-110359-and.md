# Task: review core commit 9f6c6eb9093 (#110359) and report what blocks it.

## Observation

Task: review core commit 9f6c6eb9093 (#110359) and report what blocks it.

Two observations about one call.

FIRST — typo3_task_guide subsumed typo3_hint_lookup, and I never made the hint call the skill tells me to make. Both base.md ("step 4: typo3_hint_lookup for each subsystem in scope, with its concrete paths. One query per subsystem; a single broad query is not subsystem evidence") and the skill body ("Pass them to typo3_hint_lookup for the conventions of the subsystem the patch is in, one call per subsystem, before forming a view of whether the code is right") instruct a separate call per subsystem. I made zero.

The reason is that typo3_task_guide's answer already carried a `hints` array with four full hint groups — fluid-viewhelpers, system-extension-boundaries, core-tests, fal-basics — each with its complete hint bodies, versions and scopes. Those hints did real work in the review:
- fluid-viewhelpers "ViewHelpers are covered by functional tests under Tests/Functional/ViewHelpers/, not unit tests" became the coverage finding that three ViewHelpers changed their resolution path with no ViewHelper test added.
- fluid-viewhelpers on registerArgument type enforcement and the injectable ArgumentProcessorInterface is what stopped me claiming a TypeError path was unreachable — the strict processor is the default from v14 but an installation can swap it, so I reported the finding ranked on consequence rather than dismissing it.
- core-tests "isolated logic is a unit test... a unit test of those asserts the mock" is what let me rank the ten new mock-only tests sitting in the functional suite, AND check whether the patch introduced that pattern (it did not — setUp already did it, so I reported it as not introduced by this patch).

Having read all four groups, a separate hint_lookup per subsystem would have been a re-fetch. So the skill's step 4 was satisfied by step 3's output, and the order as written asks for a call that the previous call already answered. Either the skill should say "unless typo3_task_guide already returned the hints for these paths", or task_guide should return hint IDs plus a pointer rather than full bodies so the separate call has something to add. As it stands the instruction reads as mandatory and is silently redundant, which is the kind of thing that trains a model to skip steps.

Worth naming what I lost by not calling it: I never got a dependency-injection hint. I ended up recommending `#[Autowire(lazy: true)]` for the new LinkService dependency on ResourceFactory, and I had to establish that it is an established core pattern by grepping the checkout (found it at core/Classes/Site/Set/SetRegistry.php:43, form/Classes/EventListener/DataStructureIdentifierListener.php:68, form/Classes/Domain/Configuration/PersistenceConfigurationService.php:41). A hint_lookup on service wiring might have carried that; task_guide's four groups did not, because it picked them from the paths and none of the paths reads as DI configuration.

SECOND — a small schema wart. I passed `area` and `paths` separately. The answer folded the area string into the paths array as a sixth element and scoped it: `{"path":"core Resource / extbase Service / fluid ViewHelpers","scope":"core"}`. A free-text area description was treated as a file path and given a scope verdict. Harmless here, but it means the `scopes` array cannot be read as "these are the files" by anything downstream.

## Suggestion

Decide which of the two tools owns hint delivery for a task that supplies paths. Either (a) typo3_task_guide returns hint IDs and titles only, with "call typo3_hint_lookup with id X for the body", so the skill's per-subsystem step has content to add; or (b) typo3_task_guide keeps returning full bodies and says so in its answer ("the hints for these paths are included; a separate typo3_hint_lookup is only needed for a subsystem not among them"), and the typo3-core-patch-review skill and base.md step 4 are reworded to match. Option (b) is cheaper and matches what actually happened. Either way, name in the answer which subsystems the returned hints do NOT cover, so a gap like dependency injection is visible instead of being discovered by grep. Separately: keep `area` out of the `scopes` array, or mark it `{"kind":"area"}` rather than scoping it as a path.
