# No hint says which of two colliding site bases wins, which is what a 404 at the site root usually is

## Observation

Task: "ich habe das blog setup ausgeführt, aber das frontend zeigt immer noch 404" on a DDEV TYPO3 14.3.6 installation of t3g/blog.

typo3_project_describe reported two sites in one answer, which was the single most useful thing in the session: site "main" base https://blog.ddev.site/ rootPageId 1, and site "blog" base / rootPageId 2. The backend answered, the frontend returned "Page Not Found — Reason: The requested page does not exist", and page 1 turned out to be deleted.

What decides that case is site matching, and no hint in the brief covered it. I read it out of the installed core myself: SiteMatcher::getRouteCollectionForAllSites() builds one Route per site and per language with the base's host as the route host, matchSiteByUri() hands them to BestUrlMatcher, and a route carrying a host beats a hostless one. So "main" won every request and its root page was gone. A base of "/" is not a neutral default; it is the loser whenever any other site names a host.

The brief did carry initial-content-references, whose v14 statements about Import::processSiteConfigurations() rewriting base to /<identifier>/ put me in the right neighbourhood — a 404 at the project root is a base problem — but the mechanism was a different one and its cause did not apply: this installation ships no Initialisation/, and the site was created by the core's CreateSiteConfiguration hook, which t3g/blog extends in ext_localconf.php to cover its own doktype, giving entry point autogenerated-<uid> and identifier autogenerated-<uid>-<md5>.

The same gap bit me a second time in the same session, which is why I am filing it rather than noting it. After making the extension's setup service choose its own base, I gave a second site the plain path "/probe" — and it 404'd again for exactly the reason above, because the site holding "/" carried a host. I had to carry the host over into the derived base. Two independent failures in one session from one unwritten rule.

## Query

typo3_task_guide with task "Blog extension development installation was set up, backend works but frontend returns 404 page not found", changeType operations, targetVersion 14.3, paths config/sites/blog/config.yaml, config/sites/main/config.yaml, .ddev/config.yaml

## Suggestion

Add a hint reachable from a frontend-404 symptom query stating: TYPO3 matches a request against the routes of all sites at once and a base carrying a host beats a base that does not, whatever the paths. So "base: /" works only while it is the only site; a second site under the same host must carry that host in its base; and a site whose root page is deleted or hidden still wins the match and answers "The requested page does not exist". That last part matters because the message reads like a slug problem and is in fact a site-selection problem. Naming SiteMatcher, BestUrlMatcher and CreateSiteConfiguration would let a caller verify it in the checkout.
