# The core auto-creates a site for a new root page, and the neighbouring hint sends you to the wron...

## Observation

Task: "ich habe das blog setup ausgeführt, aber das frontend zeigt immer noch 404" on a DDEV TYPO3 14.3.6 installation of t3g/blog.

The installation had a site whose configuration nobody in the repository had written and whose identifier appears in no file the extension ships. Finding where it came from cost me a grep of the whole vendor directory for a log message string. It is TYPO3\CMS\Core\Hooks\CreateSiteConfiguration, a processDatamap_afterDatabaseOperations hook that fires when DataHandler inserts a page at pid 0 or with is_siteroot and writes a site through SiteWriter::createNewBasicSite(). Four things about it decided this session and none are in the brief:

- The identifier it invents is autogenerated-<uid>-<md5 of uid>. That is what the user had later renamed by hand in the Sites module.
- The base it writes is the site URL plus /autogenerated-<uid>, or the site path plus it under CLI, because the hook cannot know the URL either. So a blog created from a backend module answers on a sub-path, never on /.
- It then calls updateSlugForPage(), which blanks the slug and lets it regenerate.
- Its $allowedPageTypes is protected and holds only DOKTYPE_DEFAULT, LINK and SHORTCUT, so it does not fire for a custom doktype unless an extension subclasses it. t3g/blog does exactly that in ext_localconf.php for its blog page doktype, which is why a site existed at all and why the extension's SetupService could call getSiteByRootPageId() without it throwing.

The brief did return initial-content-references, which states that Import::processSiteConfigurations() overwrites base with /<identifier>/ in v14 and that a seeded installation therefore answers 404 at the project root. Right neighbourhood, wrong mechanism: this installation ships no Initialisation/ and imported nothing. Following that hint I spent calls looking for an import that was never there. Two unrelated pieces of core produce nearly the same symptom — a freshly set up installation answering 404 at its root because its base is not the installation's URL — and only one of them is written down.

## Query

typo3_task_guide with task "Blog extension development installation was set up, backend works but frontend returns 404 page not found", changeType operations, targetVersion 14.3. The brief returned the hint group initial-content-references, whose v14 statements are about Import::processSiteConfigurations().

## Suggestion

Add the hook as its own statement beside initial-content-references, and cross-reference the two so a caller holding the symptom can tell them apart: a site nobody wrote, named autogenerated-<uid>-<md5>, on base <siteUrl>/autogenerated-<uid>, with the root page slug reset, comes from CreateSiteConfiguration and not from an import. Include that it fires only for doktypes 1, 3 and 4 unless an extension subclasses it to extend $allowedPageTypes, since that is what makes it fire for a custom root page doktype and what a caller reading only the core class would conclude the opposite from.
