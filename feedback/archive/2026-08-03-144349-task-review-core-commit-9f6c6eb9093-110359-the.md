## Observation

Task: review core commit 9f6c6eb9093 (#110359). The commit message justifies removing a backend compatibility path with "It compensated for links relative to the /typo3/ directory, which does not exist since v13." Settling whether that claim holds was the single most important reading in the review, because it is the stated basis for removing user-visible behaviour.

I asked typo3_changelog_lookup(query "typo3 directory backend entry point"). It returned matchCount 0, an empty entries array, an empty tags array, and the full 54-element versions list.

The tool's own description says: "When no entry carries all of them, the answer names the largest part of the query that does reach entries, which is what to ask again with." That narrowing did not happen. There was no partial-match field, no "the largest part of your query that reaches entries is X", nothing to re-ask with. The answer was indistinguishable from "the changelog has nothing about the backend entry point in any of 54 versions", which is a much stronger claim than "these four words never co-occur in a title".

Because I had nothing to re-ask with, I abandoned the server and grepped the checkout, where I found typo3/sysext/backend/Classes/Routing/UriBuilder.php:199 constructing `new RequestContext('/typo3/')`. That is what settled it — the /typo3/ URL prefix demonstrably still exists on this branch, so the commit message's stated reason does not support the removal. It became the top finding of the review.

Two separate things here, and I want to be honest about which is mine:

- The bug: the documented partial-match narrowing did not appear on a zero-match query. Whatever the implementation does when matchCount is 0, it did not do what the description promises, and a zero with no narrowing is the least actionable answer the tool can give.
- My own miss: base.md explicitly routes "does this still work in version N" to typo3_documentation_lookup, and I never called it. I went to the changelog for a question the changelog is the wrong corpus for — a changelog records change events, so a path nobody has changed has no entry — and then to grep instead of to the tool the order names. The server routed me correctly and I did not follow it. Any assessment of this feedback should count that against the session, not against the server.

## Query

typo3_changelog_lookup(query "typo3 directory backend entry point", limit 15) against a 15.0.0-dev core checkout. Returned {"matchCount":0,"tags":[],"entries":[],"versions":[...54 versions...],"answeredBy":"packages"}.

## Suggestion

On matchCount 0, return the narrowing the description already promises: the largest subset of the query terms that does reach entries, with the count each subset would yield, so the caller has a concrete re-ask instead of a dead end. For this query that would have been something like "typo3" or "backend" with their counts. Second, make the zero answer say what it is a zero ABOUT — "no changelog title carries all of these words; a changelog records change events, so a mechanism nobody has changed has no entry here, and whether it still holds in 15.0 is typo3_documentation_lookup" — so the caller is pushed to the right corpus rather than to grep. That sentence exists in base.md; the tool answer is where it would actually be read.
