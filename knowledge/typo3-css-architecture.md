# TYPO3 Core CSS Architecture Hints

This document collects practical CSS and Sass architecture hints for TYPO3 core
work. Keep it aligned with the actual files below `Build/Sources/Sass/` and
generated public assets.

## Source and Build Boundaries

- Sass source files live below `Build/Sources/Sass/`.
- Public CSS output is generated by the frontend build and should not be edited
  as the primary source when a Sass source exists.
- Run `./Build/Scripts/runTests.sh -s build` after Sass or generated asset
  changes.
- Run `./Build/Scripts/runTests.sh -s lintScss` for Sass linting.
- `lintScss` runs TYPO3's stylelint setup for `Build/Sources/Sass/**/*.scss`.
- For a focused CSS build, use `./Build/Scripts/runTests.sh -s npm -- run
  build-css`, which maps to `grunt css`.
- The Grunt CSS build runs `exec:stylefix` and `postcss`.
- The PostCSS build compiles Sass, runs Autoprefixer, minifies with cssnano, and
  adds the TYPO3 file banner.
- Some CSS-related assets have special build paths, for example CKEditor CSS
  processing in `Build/rollup/ckeditor.js`.

## Browser Target

- TYPO3 backend CSS targets evergreen browsers as they exist on the day of the
  corresponding TYPO3 LTS release.
- Modern CSS features are acceptable when they are supported by the evergreen
  browser set for that LTS release.
- CSS features may be adopted before the LTS release when the team expects them
  to be part of the evergreen browser baseline at LTS release time.
- Early adoption must be intentional, reviewable, and limited to features with a
  clear path into the LTS browser baseline.
- When CSS changes are backported to older TYPO3 versions, the CSS must fully
  match the evergreen browser baseline of that target release year.
- Do not backport CSS features that only match a newer release baseline unless
  the target branch already supports them.
- Do not add compatibility workarounds for obsolete browsers outside the active
  LTS browser target.
- When using newer CSS features, verify that the feature is reasonable for the
  current LTS release target and that the build pipeline accepts it.
- Prefer native CSS capabilities over JavaScript workarounds when the feature is
  part of the active LTS evergreen browser target.
- The Popover API is an example where native platform behavior should be
  preferred over custom JavaScript positioning or visibility logic when the
  target baseline supports it.

## Component Structure

- Prefer extending or adding focused component partials below
  `Build/Sources/Sass/component/`.
- Forms belong below `Build/Sources/Sass/component/forms/` when they style
  backend form controls.
- Scaffold-level layout belongs below `Build/Sources/Sass/component/scaffold/`.
- Dashboard styles belong below `Build/Sources/Sass/dashboard/`.
- Custom element styles usually belong below `Build/Sources/Sass/element/`.
- Keep selectors close to the owning UI component and avoid broad global
  selectors.

## Minimal CSS and Reusable Components

- Write as little new CSS as possible.
- Prefer reusing, extending, or composing existing TYPO3 backend components
  before adding new CSS.
- New CSS should express reusable component behavior, not one-off page-specific
  tweaks.
- Utility classes should be used only in exceptional cases.
- Do not use utility classes as a substitute for a missing reusable component.
- If a utility class is used, the reason should be clear from nearby context and
  it should not create hidden coupling between markup and layout.
- When a pattern appears more than once, prefer a component style or component
  custom properties over repeated local CSS.

## CSS Class Naming

- Use existing component naming conventions from nearby Sass files.
- TYPO3 backend component classes usually use a short component root plus
  hyphenated elements or variants, for example `.panel`, `.panel-heading`,
  `.panel-body`, `.toolbar-item`, `.module-docheader`, or `.dropzone-hint`.
- Prefer readable kebab-case class names.
- Do not introduce a new naming system such as BEM-style
  `block__element--modifier` unless the surrounding component already uses it.
- Variants and sizes commonly append a suffix to the component class, for
  example `.btn-sm`, `.panel-condensed`, `.card-size-large`, or `.table-fit`.
- Variants should customize behavior through custom properties whenever
  possible.
- Variant classes should mainly set component properties; the base component
  should consume those properties.
- Avoid duplicating full rule sets for variants when changing a property value
  is enough.
- State classes should be explicit and consistent with nearby components, for
  example `.active`, `.disabled`, `.selected`, `.is-*`, or `.has-*`.
- Use `t3js-*` classes only as JavaScript hooks. Do not attach visual styling to
  `t3js-*` classes.
- Keep JavaScript hook classes separate from styling classes when both are
  needed on the same element.
- Prefer component-local custom properties over additional modifier classes when
  only token values or state colors need to change.
- Avoid generic new class names that could collide globally, especially for
  reusable backend components.

## Styleguide Demos

- All CSS components must be represented with demos in the styleguide extension.
- New CSS components need a matching styleguide demo.
- Changed CSS components should update an existing styleguide demo or add one
  when no demo exists.
- Backend component demos usually live below
  `typo3/sysext/styleguide/Resources/Private/Templates/Backend/Components/`.
- Styleguide demos should cover relevant variants, states, sizes, icons, empty
  states, disabled states, interaction states, light and dark mode, and
  RTL-sensitive layout when applicable.
- A CSS component change without styleguide coverage should be treated as
  incomplete unless there is a clear reason documented in the patch.

## Design Tokens and Variables

- Prefer existing variables, CSS custom properties, Bootstrap variables, and
  TYPO3 component conventions.
- Prefer existing `--typo3-*` custom properties for TYPO3 backend colors,
  spacing, borders, shadows, transitions, and state styles.
- Avoid hard-coded colors, spacing, z-index values, or breakpoints when an
  existing token or variable exists.
- Keep theme and dark-mode behavior in mind when changing colors or state
  styles.
- Avoid creating a local one-off token unless the value is repeated or has clear
  semantic meaning.
- Component-local custom properties are useful when they map a component concept
  to global TYPO3 tokens, for example `--my-component-bg:
  var(--typo3-component-bg)`.
- Avoid bypassing the token system with raw hex, RGB, or HSL values unless the
  value is truly external, brand-specific, or already established nearby.

## Color and Surface Tokens

- Treat `--token-color-*` values as low-level palette tokens.
- Do not use `--token-color-*` values directly in component CSS.
- Palette tokens define the color space and are used to create semantic tokens.
- When palette tokens are used to define a semantic token, pick explicit light
  and dark values with `light-dark(...)`.
- Prefer semantic TYPO3 tokens over direct palette tokens in component CSS.
- Use `--typo3-text-color-*` for text and icon colors.
- Use `--typo3-surface-*` for larger page, scaffold, and base background areas.
- Use `--typo3-surface-container-*` for cards, panels, list items, table areas,
  and nested component backgrounds.
- Surface tokens may be used directly, but they must follow the logical layering
  order of the UI.
- Follow the surface container elevation sequence intentionally: `lowest`,
  `low`, `base`, `high`, `highest`.
- Do not jump to a higher surface token just to create contrast. Prefer the
  token that matches the component's layer and use borders, shadows, or state
  tokens for emphasis.
- Nested components should move through the surface sequence deliberately so
  parent and child layers remain understandable in light and dark modes.
- Use matching `*-text` surface tokens, such as
  `--typo3-surface-container-warning-text`, when placing text or icons on a
  stateful surface.
- Use `--typo3-component-bg`, `--typo3-component-color`,
  `--typo3-component-border-color`, and related component tokens for generic
  component containers.
- Use `--typo3-state-*` tokens for interactive or semantic states such as
  default, primary, success, info, warning, danger, notice, hover, focus,
  active, and disabled states.
- Derive subtle borders and separators with `color-mix(...)` from semantic
  tokens and `--typo3-border-mix` instead of hard-coded colors.
- Do not pair arbitrary foreground and background tokens. Choose token pairs
  that are intended to work together in light and dark modes.
- Prefer component-local aliases, for example `--panel-header-bg:
  var(--typo3-surface-container-low)`, when a component needs a named internal
  color role.

## Shadow Tokens and Layering

- Shadows must follow the same logical layering model as surfaces.
- Prefer semantic shadow tokens over raw `box-shadow` values.
- Use component shadow tokens such as `--typo3-component-box-shadow`,
  `--typo3-component-box-shadow-strong`, `--typo3-component-box-shadow-tooltip`,
  `--typo3-component-box-shadow-flyout`, `--typo3-component-box-shadow-dialog`,
  and `--typo3-component-box-shadow-window`.
- Use stronger shadows only for higher layers such as flyouts, dialogs,
  popovers, tooltips, overlays, and windows.
- Do not use shadows as decoration when a component is not elevated in the UI
  hierarchy.
- Keep surface elevation and shadow strength aligned. A high shadow on a low
  surface usually indicates the wrong token choice.
- Prefer component-local aliases, for example `--popover-box-shadow:
  var(--typo3-component-box-shadow-flyout)`, when a component needs a named
  internal shadow role.

## Light and Dark Mode

- CSS changes must work in both light and dark backend color schemes.
- Prefer semantic TYPO3 custom properties such as surfaces, text colors,
  component colors, input colors, and state colors over fixed light or dark
  values.
- Use existing `light-dark(...)` patterns when a value genuinely needs distinct
  light and dark variants.
- Keep `color-scheme` behavior and inherited custom properties in mind when
  adding component-level styles.
- Check contrast for text, icons, borders, focus outlines, and state backgrounds
  in both schemes.
- Do not introduce a light-only assumption such as dark text on a fixed bright
  background unless the component explicitly controls both foreground and
  background.

## CSS Custom Properties

- Use custom properties to express component API and state, especially for
  colors, spacing, borders, shadows, and transitions.
- Define component-local properties near the component root and consume them in
  child selectors.
- Use semantic names that describe intent, for example `--upload-queue-item-bg`,
  not the current visual value.
- Prefer fallback-free `var(...)` when the referenced TYPO3 token is expected to
  exist globally.
- Use `color-mix(...)` with TYPO3 tokens for derived borders, hover states, or
  subtle backgrounds instead of hard-coded derived colors.
- Avoid deep chains of aliases when a direct semantic token is clearer.
- For variants, prefer setting custom properties on the variant class and keep
  structural declarations in the base component.
- Only add variant-specific declarations when the variant changes layout,
  structure, or behavior in a way that cannot be expressed through properties.
- Components should expose a small, named custom property contract when
  variants, host context, or states need to tune the component.
- The base component should consume component properties, while variants and
  state selectors primarily set property values.

## Web Components and Element Styles

- Styles for TYPO3 custom elements should start at the custom element host
  selector, for example `typo3-backend-combobox`.
- Keep custom element Sass files below `Build/Sources/Sass/element/` when the
  style belongs to a web component.
- Use CSS custom properties as the main styling API between host, variants, and
  internal parts.
- Use `::part(...)`, slots, and explicit host attributes as stable styling
  boundaries for custom elements.
- Do not style arbitrary internal DOM depth of a custom element when a host
  selector, part, slot, or custom property can express the contract.
- Keep custom element CSS aligned with the TypeScript component API and update
  generated assets together.

## State Attributes and Semantic Selectors

- Prefer semantic attributes and explicit state APIs over ad hoc visual classes
  for component state.
- Use attributes such as `[disabled]`, `[aria-selected="true"]`,
  `[aria-expanded]`, `[aria-current]`, or component-owned `data-*` attributes
  when they represent the actual state.
- ARIA attributes must reflect real accessibility state and must not be
  introduced only as CSS hooks.
- State selectors should map to component properties whenever possible.
- Keep JavaScript, markup, CSS, and tests in sync when a state attribute is
  added, renamed, or removed.

## Selector and Specificity Rules

- Keep specificity low and predictable.
- Avoid `!important` unless overriding external or unavoidable generated styles.
- Avoid styling by brittle DOM depth when a component class or state class can
  express the intent.
- Prefer explicit state classes and attributes over selectors that depend on
  visual position.

## Z-Index and Overlay Layering

- Prefer existing z-index tokens such as `--typo3-zindex-dropdown`,
  `--typo3-zindex-modal-backdrop`, `--typo3-zindex-modal`, and
  `--typo3-zindex-header`.
- New overlays, flyouts, menus, sticky headers, dialogs, and popovers must be
  placed deliberately in the backend layering model.
- Avoid raw z-index numbers when an existing token matches the intended layer.
- Do not use extremely high z-index values to win stacking conflicts. Fix the
  owning stacking context or use the correct layer token.
- Keep z-index, shadow strength, and surface elevation aligned.

## Motion and Transitions

- Prefer existing transition tokens such as `--typo3-transition-color` for
  interactive color, border, shadow, and opacity transitions.
- Motion should support the user's reduced motion preference.
- Add `@media (prefers-reduced-motion: reduce)` handling for new transitions or
  animations that move, resize, fade large regions, or affect focus/navigation.
- Avoid `transition: all` unless the surrounding component already uses it and
  the affected properties are intentionally constrained.
- Keep motion functional and subtle. It should clarify state changes, not create
  decorative noise.

## Container Queries and Responsive Components

- Prefer component-local responsiveness over viewport-only breakpoints when a
  component can appear in different backend containers.
- Use `container-type: inline-size` and container queries for reusable
  components when the component layout depends on available container width.
- Container queries are an example of a modern CSS feature that may be
  introduced before an LTS release when they are expected to be part of the LTS
  browser baseline.
- Keep container query rules scoped to the owning component.
- Do not add global breakpoints for a component-specific layout problem unless
  the behavior is truly tied to the viewport or scaffold.
- Verify container-query behavior in narrow module columns, sidebars, dialogs,
  and full-width module content when applicable.

## RTL and Logical Properties

- All backend components must be checked for RTL support.
- Prefer logical properties over physical left/right properties.
- Use `margin-inline-*`, `padding-inline-*`, `inset-inline-*`,
  `border-inline-*`, and logical `float` or positioning patterns where
  applicable.
- Prefer TYPO3 position custom properties such as `--typo3-position-start`,
  `--typo3-position-end`, `--typo3-position-start-percent`,
  `--typo3-position-end-percent`, and `--typo3-position-modifier` when
  direction-aware calculations are needed.
- Avoid new `left`, `right`, `margin-left`, `margin-right`, `padding-left`,
  `padding-right`, `border-left`, and `border-right` rules unless the physical
  side is intentional and documented by nearby context.
- Direction-aware transforms should account for `--typo3-position-modifier` when
  horizontal movement or rotation depends on reading direction.
- Components with icons, carets, flyouts, drag handles, resize handles, trees,
  lists, tables, toolbars, and form controls need explicit RTL review.

## Accessibility and States

- Preserve visible focus styles.
- Color contrast must satisfy WCAG requirements.
- Text, icons, borders, focus outlines, state backgrounds, disabled states, and
  subtle helper text must be checked for sufficient contrast.
- Interactive elements must have visible focus styles.
- Interactive elements must be reachable and operable by keyboard.
- Keyboard focus must be visible when navigating with Tab, Shift+Tab, arrow
  keys, or component-specific keyboard interaction.
- Prefer `:focus-visible` for visible keyboard focus when pointer focus should
  not show the same treatment.
- Do not remove outlines unless an equivalent or better keyboard focus indicator
  is provided.
- Keyboard focus order should remain logical and match the visual/component
  order.
- Components must not trap keyboard focus unless they intentionally manage a
  modal or composite widget interaction and provide an escape path.
- Interactive elements must have hover styles when hover interaction is
  relevant.
- Focus and hover styles must be present for buttons, links, menu items, toolbar
  items, form controls, tabs, tree items, table actions, drag handles, and
  custom elements.
- Check hover, focus, active, disabled, loading, empty, error, selected,
  expanded, collapsed, and high-contrast states when applicable.
- Do not rely on color alone to communicate state.
- Drag and drop, modal, toolbar, navigation, and form changes need extra
  attention for keyboard and screen-reader workflows.
- Focus styles should use existing TYPO3 focus, outline, state, and border
  tokens where possible.
- Hover and focus states should use `--typo3-state-*` tokens or component-local
  state properties that map to them.
- Verify contrast in both light and dark color schemes.

## Icons, Text, and Layout Stability

- Components that combine icons, labels, badges, carets, and actions must keep
  layout stable across hover, focus, active, loading, and disabled states.
- Decorative icons should be hidden from assistive technology with
  `aria-hidden="true"` or equivalent markup.
- Interactive icon-only controls need an accessible name.
- Use logical spacing for icon and text gaps, for example `margin-inline-*` or
  `gap`, so RTL layouts remain correct.
- Define overflow behavior for long labels in compact backend UI, for example
  wrapping, truncation, or explicit min/max sizing.
- Hover and focus styles must not cause avoidable layout shifts.

## Bootstrap and TYPO3 Backend UI

- TYPO3 still uses Bootstrap CSS in parts of the backend.
- Bootstrap usage is being actively reduced over time.
- Treat Bootstrap as existing infrastructure, not as the preferred target
  architecture for new TYPO3-specific UI.
- Prefer TYPO3 component styles, CSS custom properties, and local conventions
  for new backend UI behavior.
- Reuse existing Bootstrap utility or component conventions only when the
  surrounding code already depends on them and no TYPO3-specific component
  boundary is needed.
- Avoid introducing new high-specificity Bootstrap overrides; introduce a TYPO3
  component style when behavior is TYPO3-specific.
- Many Bootstrap utilities are intentionally disabled in TYPO3's Sass
  configuration.
- Do not depend on disabled Bootstrap utilities or recreate them as local
  one-off classes.
- Keep backend UI changes consistent with nearby components in
  `Build/Sources/Sass/component/`.

## Generated Assets

- If generated CSS or JavaScript changes are committed, verify the corresponding
  source change exists.
- Do not hand-edit generated public assets as the only change.
- When TypeScript and Sass interact through class names or custom elements, keep
  naming stable and update tests or selectors together.

## Review Checklist

- Does the change live in the correct Sass partial?
- Does it reuse existing variables or tokens?
- Does it use semantic surface, text, component, or state tokens instead of raw
  palette values?
- Does it avoid direct `--token-color-*` usage in component CSS?
- Does surface usage follow the logical layer sequence?
- Does shadow usage match the component's elevation layer?
- Are foreground/background token pairs valid in both light and dark modes?
- Does it avoid unnecessary new CSS by reusing an existing component?
- Is any utility-class usage exceptional and justified?
- Does the class naming follow nearby component conventions?
- Do variants customize the base component through custom properties where
  possible?
- Are `t3js-*` classes used only as JavaScript hooks and not as styling
  selectors?
- Does it use semantic `--typo3-*` custom properties where available?
- Does it work in both light and dark color schemes?
- Are WCAG color contrast requirements met for text, icons, borders, focus
  outlines, and state backgrounds?
- Do all interactive elements have visible focus styles?
- Are all interactive elements reachable and operable with keyboard navigation?
- Is keyboard focus visible with `:focus-visible` or an equivalent pattern?
- Does focus order remain logical, and are intentional focus traps handled
  safely?
- Do hoverable interactive elements have hover styles?
- Does it use logical properties for RTL support instead of physical left/right
  rules?
- Were direction-aware transforms, icons, carets, flyouts, and handles checked
  in RTL?
- Is there a matching styleguide demo for every new or changed CSS component?
- Does the styleguide demo cover relevant states, variants, light/dark behavior,
  and RTL-sensitive layout?
- Are selectors scoped to the owning component?
- Are focus and disabled states covered?
- Are generated assets in sync?
- Were `build` and `lintScss` considered or executed?
- Was stylelint executed through `lintScss` for Sass source changes?
- Would `npm -- run build-css` be enough for an iteration, or is the full
  `build` suite needed?
- Is the CSS feature compatible with the evergreen browser target for the TYPO3
  LTS release?
- If a feature is adopted before the LTS release, is it expected to be part of
  the LTS browser baseline?
- For backports, does the CSS fully match the evergreen browser baseline of the
  target release year?
- For custom elements, does styling use host selectors, custom properties,
  slots, or `::part(...)` as stable boundaries?
- Are ARIA and `data-*` state selectors backed by real component state?
- Does any new overlay use the correct z-index token and stacking context?
- Do new transitions or animations respect reduced motion?
- Would a container query be more appropriate than a viewport breakpoint?
- Do icons and labels remain accessible, RTL-safe, and layout-stable across
  states?
