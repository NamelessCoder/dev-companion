# R-FBK-005 — A feedback is attributed to the model that left it

**A feedback carries the model that recorded it, and one that was not attributed
says so rather than carrying nothing.**

Much of what arrives is not about an answer but about a session: a skill whose
steps were loaded and not run, a tool nothing reached for, an order that was
read and then inverted. That is behaviour, and behaviour belongs to one model.
Unattributed, two models' habits arrive as one undifferentiated report, and the
question the feedback actually poses — is the instruction missing, or was it
present and not followed — cannot be asked of it.

The model is asked for rather than inferred: the handshake names the client, not
the model behind it. The write never fails on it, because a feedback is worth
more than its attribution, and a model that does not know its own identifier
sends `unknown` rather than an invented one — an attribution nobody can trust is
worse than a missing one. So the field is always written, `unknown` included,
which is also what a feedback recorded before the field existed reads as.

## From

The feedback of 2026-07-31 17:21 reporting that the conformance skill's
instructions were loaded and its lookups were not run — recorded from a site
package whose published skill was byte-identical to this repository's, base and
checklist included, so the gap it named was not in the text the session had. The
one thing that would have made it actionable, which model read those steps and
walked past them, was the one thing the feedback could not carry.
