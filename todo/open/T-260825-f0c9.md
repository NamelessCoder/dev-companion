# Say whether a patch set carries git conflict markers

Step 2 of the ladder, delivery, judged into `D-ANS-121` on 2026-08-27: the fact
is here and reachable only through a parameter the task did not know to set, so
what moves is placement rather than knowledge. That entry holds the reading —
where Gerrit writes the fact, how often it is true, and why the shape the
feedback asked for is wrong on 7 of the 8 open changes it would fire on.

Give a change read by name two fields. `conflicts` is the paths named by the
conflict message on the **current** patch set, empty where that patch set
carries none and null where the log was not read; the message is matched on "The
following files contain Git conflicts:" and held against its own
`_revision_number`, because a rebase writes the same list and a message about a
superseded patch set is history. `cherryPickOf` is the change and patch set this
one was cherry-picked from, read off `cherry_pick_of_change` and
`cherry_pick_of_patch_set`, which the payload already carries. `Gerrit::named()`
asks `o=MESSAGES` on every call for it and `messages` keeps deciding what the
caller is handed; the search and the enumeration ask for neither and answer
`conflicts` null. The text half says it beside the standing line, and says which
of the two a reader is looking at: a patch set that is broken rather than one
nobody has reviewed.

Both halves are `src/` and a declared output schema, which is why this waits.
Change 93689 is the open case to hold it against, and 95412 the one the report
came from.
